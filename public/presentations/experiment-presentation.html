FX Replay Growth Challenge · Experiment Proposal
A/B Experiment

Landing density vs. free-tier signup conversion

A walk-through of the A/B test I built — the hypothesis, the two versions competing, how I measure the result without winning on false ground, what triggers each decision, and how I wired it end-to-end in PostHog. All of it derived from the manual audit I ran on fxreplay.com's current signup flow.

Follows the classic H · C · V · M · D framework — Hypothesis, Control, Variant, Success Metric, Decision.

Context

Three opportunities to improve CVR

To build the "Try FX Replay Free" proposal for the challenge, I started by analyzing the current fxreplay.com landing. From that analysis, concrete improvement opportunities emerged that then guided the value proposition of the landing I built for the challenge. The audit surfaced three CVR improvement opportunities: two were solved by product decisions in the new experience, and the third is what this A/B experiment tests.

Improvement opportunities detected:

Chargebee on the free path. Checkout language ("Complete your order", "Subscribe") appears before any value is delivered. The new signup doesn't touch Chargebee.

Pricing gate immediately after signup with buggy currency conversion. No pricing on the free path in the new flow.

Content overload on the landing — 120+ assets with per-card detail, 12 indicators with paragraph descriptions, dense feature grids. This is what the A/B tests.

H — Hypothesis

Less text converts better than more text.

A landing with less text converts more visitors into registered users than a text-heavy landing does, because the retail-trader audience decides quickly based on trust signals (testimonials, "no card required") and on the clarity of the main action (the signup button), not on reading every product detail.

Why I believe this

  • Signup intent is high but fragile. If a user made it to the landing at all, they're already interested in trying the tool. Giving them more to read (specs, tabs, per-card details) adds mental load without adding trust — and many bail before converting.
  • What actually convinces this audience is different from what the current landing shows. A testimonial from another trader, the "no card required" promise, the "no trial that expires" detail — all of that carries far more weight than a paragraph describing a technical indicator.
  • Deep product detail has its place, but not here. It's the right content for someone already inside the product evaluating a paid plan — not for an anonymous visitor deciding whether to try the free version.
C — Control

LandingVerbose — the version with a lot of text

The control in an A/B test is the baseline you compare against. I chose to replicate the information density fxreplay.com's current landing has — precisely because the hypothesis is that density hurts. If this version loses to the other, the conclusion is that less is more.

Careful — two things vary at the same time

  • Content quantity — the variant has ~50% less scroll.
  • Headline tone — the variant uses an emotional promise instead of a descriptive one.

Both move together in this test, so if it wins we won't know which one pulled the weight. A follow-up test would isolate each variable — it's a conscious trade-off to save time now.

With more UX time: I would have polished the copy and the amount of information trimmed in variant A, and improved the signup and welcome screens beyond their current state. Most of the project time went into the two landings and into wiring the pipeline end-to-end with PostHog, so signup and welcome shipped functional but without the iteration they would ideally deserve.

M — Success metric

How I decide if the variant won

CVR (Conversion Rate) is the percentage of visitors who saw the landing and ended up signing up. Sliced by variant means I look at that percentage separately for each version (control vs. variant_a) so I can compare them.

Primary metric: CVR = signup_succeeded / landing_viewed, sliced per variant.

How it reads in PostHog: the pipeline is already wired. Both events (landing_viewed and signup_succeeded) carry the variant property in their payload, so PostHog can segment automatically. I build a funnel — step 1 landing_viewed → step 2 signup_succeeded — with breakdown (segmentation) by variant. The output is two bars: one per version, each with its CVR.

Sample size

How many users I need before I can trust the result

Before running the experiment I need to know how many users each variant has to see so that the difference between the two is statistically reliable — not a coincidence. That number is computed from four parameters:

How much the landing converts today — 5%

The percentage of visitors who already sign up, before the experiment. I assume 5% because I don't have access to fxreplay.com's real PostHog; it's a typical average for SaaS free-tier landings.

The smallest improvement I want to be able to detect — +10%

If the variant improves CVR by less than this, the test marks it as "not significant" and I don't ship it. I picked 10% because below that it rarely justifies keeping two versions live.

Risk of a false winner I accept — 5%

5% chance the test says "variant A won" when it didn't win anything. It's been the industry standard for decades.

Risk of missing a real winner I accept — 20%

20% chance that if variant A did win, the test fails to detect it. Also standard.

Result: with these four parameters, the standard statistical formula gives me ~500 sessions per variant minimum. If fxreplay.com's real CVR were lower than 5%, the number grows — detecting the same improvement on a smaller base is harder.

With more time: I would have measured the actual baseline CVR of fxreplay.com before assuming 5% — the sample size shifts a lot with that number. Without access to their analytics, public benchmarks were the honest proxy.

D — Decision criteria

What I do with each type of result

The decision thresholds are defined before looking at any results. It's how I avoid the classic bias of "the data convinced me now that I've seen it" — a typical enemy of experiments.

Variant A converts at least +10% better than control, the difference is statistically significant (p < 0.05), AND no guardrail dropped by more than 5%
Ship variant_a
Variant A converts at least -5% worse than control, and the difference is significant
Reject variant_a
The difference lands between -5% and +10%, OR we don't reach statistical significance (p ≥ 0.05)
Keep running
CVR improved BUT a critical guardrail (e.g., signup_completion) dropped by more than 15%
Reject — uplift is artificial

The decision is rule-based, not subjective. Guardrails prevent the classic "we shipped a winner that broke something we weren't measuring" failure mode.

With more time: I'd create an agent in the project that runs these calculations for me — sample size, statistical significance, guardrail checks — and connect the PostHog MCP so it pulls the experiment's real data straight into the chat. Today I have the decision matrix defined in text and the pipeline observable in PostHog; with the agent + MCP, the loop closes without leaving the editor: I ask "how is the test going?" and it answers with numbers and a recommendation grounded in these same rules.

Implementation

How traffic is split and how the app picks a version

A feature flag is a remote switch that decides what each user sees. In this case, when a visitor reaches /, PostHog assigns one of the two versions and the assignment sticks to their unique identifier — next time they return, they see the same version.

Flag configuration in PostHog

  • Flag name: landing_density
  • Type: multivariate (supports more than two values; today uses two).
  • Split: 50% control / 50% variant_a. Assignment is stable per user — each visitor always sees the same version.
  • Rollout: 100% of traffic enters the experiment.

How the code picks the version

In app/page.tsx, when the landing loads the variant is resolved in two steps:

const [variant, setVariant] = useState<Variant>('control')

useEffect(() => {
  // 1) If the URL carries ?v=variant_a, we force it manually
  //    (useful for preview / QA without depending on the flag).
  const override = new URLSearchParams(window.location.search).get('v') as Variant | null
  if (override && KNOWN_VARIANTS.includes(override)) {
    setVariant(override); return
  }
  // 2) Otherwise, ask PostHog which one this user got.
  setVariant(getVariant('landing_density', 'control') as Variant)
}, [])

How I confirmed it works

  • The experiment_variant_assigned event fires the first time a user resolves the variant — so PostHog shows the exact moment of assignment.
  • I verified the split from the command line: curl POST /decide/ with 10 synthetic identifiers returned exactly 5 control and 5 variant_a. The split works.

Bug detected: validating the pipeline end-to-end I noticed app/signup/page.tsx hardcodes variant='control', so right now users coming from variant_a are being registered as control in the post-landing events (signup_*, welcome_viewed).

Why it happened: I set myself a 6-hour effective time-box and prioritized closing the landings and the PostHog pipeline.

How I'd catch it in my daily workflow: by adding an agent to the AI-native workflow that reviews the code before every commit and detects this kind of broken cross-file propagation. Fix estimated for this specific bug if I had to do it now: ~2 min with AI (a VariantContext propagated to the trackers).

A note on results

Everything that can be verified today

What you can see today in PostHog

The experiment is running. In the PostHog project the reviewer can confirm three concrete things:

  • Feature flag landing_density active, multivariate, 50/50 split between control and variant_a, rolled out to 100% of traffic.
  • Funnel insight landing_viewed → signup_succeeded with breakdown by variant — showing the CVR per version (with the little data from my own tests, ~30% overall, but the pipeline proves the number is calculated correctly).
  • Live activity feed with the 11 typed events firing in order — landing_viewed, cta_clicked, signup_viewed, signup_started, signup_submitted, signup_succeeded, identify, welcome_viewed — each with its correct props including variant.

Validate the setup by hand

  • /?v=control → renders the text-heavy landing (LandingVerbose).
  • /?v=variant_a → renders the minimal landing (LandingMinimal).
  • Without a query param, PostHog assigns and sticks to the user identifier.
  • The activity feed shows every event with the correct variant.

Small note: post-landing events (signup_*, welcome_viewed) currently ship with variant='control' hardcoded in app/signup/page.tsx. It's broken cross-file propagation the compiler can't catch. In production I'd catch it with a pre-commit code-review agent — exactly the kind of gap that gets added to the AI-native workflow as it emerges. Fix estimated at ~2 min with AI (a VariantContext).
