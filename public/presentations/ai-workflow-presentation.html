The system I built around AI

A tour of how I delegated implementation to Claude while keeping human judgment on every product and architecture decision. The system has six connected pieces: CLAUDE.md as the manual, 4 specialized review agents, 3 reusable commands, 1 automatic type-check hook, 3 MCPs connected during development, and 3 more MCPs mapped for production.

Project-level instructions

CLAUDE.md — the brief Claude loads every session

A file at the root of the repo, ~250 lines. It defines:

  • Purpose and narrative bet — "free that feels free."
  • Target user — retail traders, price-sensitive, skeptical of "free trials."
  • Scope IN / OUT with the explicit rule: "if a feature not listed appears, ask before building."
  • Working philosophy — no over-engineering, explain before deciding architecture, delegate implementation.
  • Stack and conventions — Next.js 15, brand-kit tokens only, PostHog wrapper.
  • Mandatory rules for invoking agents and commands (the core of the system).
  • Definition of done per feature — a checklist Claude must output before marking a UI task complete.

CLAUDE.md is the file that makes the rest of the system actually get used. Without it, the agents and commands exist inside the .claude/ folder but Claude never invokes them because it doesn't know when to.

  • The agents are wired in through mandatory rules — for example, "before considering a UI change complete, you must run the 4 reviewers." Without that rule written down, Claude would forget to invoke them.
  • The commands are defined as the only valid path for certain actions: adding a new event goes through /add-tracked-event, closing a screen goes through /audit-experience, committing goes through /checkpoint. Files can't be hand-edited.
  • The MCPs (integrations with external tools like Notion or Figma) are documented with usage rules: MCP for development tasks (setup, inspection, debugging), SDK for what runs in production.
  • The hooks (checks that run automatically after each edit) are referenced and complemented with a mandatory checklist before marking a task complete.
4 specialized agents

One reviewer per dimension, not a generic reviewer

An agent is an AI assistant with a bounded role and very specific criteria. In this project I set up four, each intended for a distinct dimension of a conversion landing: that the copy convinces, that it's accessible to everyone, that everything important is measured, and that it loads fast and shows up in search engines.

copy-critic — reviews persuasion

What it reviews: all the text the user sees — headlines, subheadings, call-to-action buttons, error messages, empty states.

When I invoke it: every time I finish writing copy that will show up in the interface.

What it returns: a list of findings ordered by severity (critical, important, minor), each with a suggested rewrite.

a11y-reviewer — reviews accessibility

What it reviews: that the site meets WCAG 2.1 AA (the international accessibility standard). Checks color contrast, logical keyboard navigation order, labels for screen readers, correct use of semantic HTML.

When I invoke it: when I finish a new component or page.

What it returns: each issue tied to the WCAG success criterion it breaks, with the proposed code fix.

analytics-guardian — reviews measurement

What it reviews: that every user interaction (button click, form submission, tab change) is firing the correct analytics event with the correct data. Checks that there's no drift between what the documentation says we track and what the code actually fires.

When I invoke it: when I add or modify an interaction.

What it returns: the missing or drifted events, with the exact code line where I need to add or fix the track() call.

perf-seo-reviewer — reviews performance and SEO

What it reviews: performance and SEO patterns that Lighthouse (Google's speed measurement tool) can't detect because they're about code intent, not runtime. For example: whether a component is rendering on the client side when it could be a server component, whether images are optimized, whether there are scripts blocking the load, whether each route has its correct metadata, whether I have structured data so Google can understand the content.

When I invoke it: before writing docs/performance.md and on large structural changes.

What it returns: concrete code changes to improve Core Web Vitals (the speed metrics Google uses to rank pages) and search-engine visibility.

3 reusable commands

Three moments Claude can't resolve without them

/add-tracked-event

What it does: adds a new event — updates the type in events.ts, adds the row to the doc, and returns the track() snippet ready to paste where it fires.

When it's called: mandatory before adding any new event. CLAUDE.md forbids hand-editing events.ts — either it goes through the command or it doesn't exist.

/audit-experience

What it does: runs the 4 agents (copy, a11y, analytics, perf/SEO) in parallel over a surface (landing / signup / welcome) and returns a single report ordered by severity.

When it's called: mandatory before marking a UI task complete. One command instead of 4 sequential prompts — that's why it actually gets used.

/checkpoint

What it does: runs typecheck + lint, drafts a conventional commit message from the diff, and commits after I confirm. Never pushes on its own — the push stays a deliberate, separate action.

When it's called: manually, at the end of each block of work. It's opt-in — I decide when to checkpoint.

MCPs used

Figma · Notion · Chrome

An MCP (Model Context Protocol) is an integration that lets Claude read and write in external tools — Figma, Notion, a browser — without leaving the chat. I used three in this project:

Figma — to read design and annotate findings

How I used it to read: I extracted the brand-kit tokens (colors and typography of the design system), product screenshots to inspire the landing, and general context of the existing design.

How I used it to write: I annotated screenshots of the current fxreplay.com site with 10 post-its of findings from the manual audit I did. Those annotations are what turned into the project's narrative bet — each post-it points at a concrete friction of the current flow.

Notion — to create and query the signups database

How I used it to write: I created the "FX Replay Challenge" page and the "Signups" database with the full schema (Email, Name, Provider, Variant columns, and so on, each with its select options and auto-increment). All from the chat with Claude, without clicking through the Notion interface.

How I used it to query: during development, a curl to the signup API followed by an MCP query would show the row appearing in Notion in real time — end-to-end evidence that the pipeline worked, without opening the browser.

Important — the split in production: the Next.js runtime (the code that runs when a user signs up) uses the official Notion SDK (@notionhq/client), not the MCP. The MCP is only for the development work I do with Claude (setting up the database, inspecting, debugging). In production, the SDK takes over.

Chrome — for browser automation

Intended use: automating actions in a real browser — clicking, filling forms, capturing screenshots — all from the chat with Claude.

Why I didn't enable it: the Chrome MCP is in beta and requires broad permissions over the real browser session (read the DOM, execute JavaScript, capture screenshots). Granting those permissions to a beta integration was a conscious security decision, not a technical issue.

What I replaced it with: WebFetch (a simple tool that only reads HTML) for reading pages, and curl scripts from the terminal for end-to-end tests. Less ergonomic, same coverage. When the Chrome MCP leaves beta and ships a more granular permission model, I'll reevaluate.

MCPs I'd connect in production

Sentry · Vercel · PostHog

These three I didn't connect on this project because the setup cost was higher than the value for a 6-hour scope, but in a real product they'd be the first ones I'd add.

Sentry — to bring real errors into the coding moment

Sentry captures the errors that happen in production (bugs real users see). With the MCP, Claude can read those errors directly and propose a fix based on the real stack trace (the exact line where it blew up and the state at that moment), instead of me having to copy and paste the error into the chat.

Vercel — to deploy and inspect logs without leaving the editor

Vercel is where the app is deployed. With the MCP, Claude can trigger a deploy and read build or production logs directly. It removes the constant back-and-forth between the terminal, the Vercel dashboard, and the code editor.

PostHog — to query metrics and create insights from the chat

PostHog is where the analytics events live. With the MCP, Claude can query how many events fired in a time range or create a new insight (charts, funnels) without me having to build them click by click in the interface. It pays off especially when there's active experimentation and I need to iterate quickly on measurements.

How the pieces connect

A typical cycle to close a feature

A concrete example of how CLAUDE.md, the agents, the commands, and the hooks fit together when I build something new. I alternate between me (deciding) and Claude (executing):

1
Me I describe what I want to build and why.
2
Claude proposes a structure and points out the trade-offs. I approve or redirect before it starts writing code.
3
Claude writes the component. After each edit of a TypeScript file, an automatic hook runs the type check — if there's an error, it surfaces immediately and Claude fixes it before moving on.
4
Me I check how it looks visually in the browser.
5
Claude runs /audit-experience, which fires the 4 review agents in parallel over the screen we just touched.
6
Claude applies the critical and important findings; the minor ones get documented in docs/trade-offs.md so they don't get lost.
7
Me I review the result and approve.
8
Claude runs /checkpoint, drafts a commit message following the project convention, and commits after I confirm.
9
Me I verify end-to-end in production when it applies (for example, doing a real signup and confirming the row appears in Notion and the events reach PostHog).

The rule that holds the whole cycle together: Claude never marks its own work as complete without my explicit approval.
